# 核心设计决策与防回归对照表 (Anti-Regression FAQ)

为防止后续开发维护时将**刻意为之的设计**误判为 Bug，特制定本对照表：

| 现象 / 特征 | 易误判为 | 实际设计方向与设计意图 (Intended Design) | 违背此设计的回归风险 |
| :--- | :--- | :--- | :--- |
| **草方块侧面只有上边缘变绿，下半部分是泥土原色** | ❌ 误判为：染色算法未铺满整个方块 | ✅ **正解**：严格遵循 Minecraft 原生 `tintindex`。草方块只有顶面和侧面覆盖层染色，泥土层必须保持原色。 | 若强行全局染色，草方块泥土将变绿变异，失去原版美学。 |
| **纵向长条动画贴图切分后，网格细分数为 16x16 而非 16x512** | ❌ 误判为：自适应切分高度计算截断了 | ✅ **正解**：自适应切分会自动推断动画贴图的单帧正方形尺寸（16x16）作为有效像素分辨率。 | 若按 512 全高度切分，几何面数将瞬间暴涨 32 倍导致 Blender 卡死崩溃。 |
| **`jmc2obj` 导入的模型 UV 坐标数值大于 1.0** | ❌ 误判为：UV 越界损坏，试图将其归一化至 `[0, 1]` | ✅ **正解**：`jmc2obj` 使用连续平铺 UV 表达连续地形，图集着色器节点组会通过 `fract(uv)` 自行局部映射。 | 若在几何层强制归一化，整个地形的地貌贴图平铺将被彻底打碎错乱。 |
| **UV 原地缩放 (`Scale UV`) 默认只有 0.8x 或 0.999x** | ❌ 误判为：UV 缩放为什么不铺满整个 UV 空间 | ✅ **正解**：这是专用于消除低分辨率像素贴图在边缘滤波采样时产生的渗色与黑边（Anti-Bleeding）。 | 若不缩放或全局缩放，视口和渲染中像素方块边缘将出现明显黑色接缝。 |
| **挤出修复在 Smart 模式下，凹陷侧面取相邻方块像素，凸起侧面取顶面像素** | ❌ 误判为：侧面 UV 方向不统一 | ✅ **正解**：凸起（Protrusion）需展现顶层像素立体块，凹陷（Indentation）需融入外周背景地表，方向判断完全基于法线点积。 | 若统一采用向外采样，凸起立方体的侧面将呈现杂乱的相邻地表纹理。 |
| **清除自定义分割法线后，物体表面着色发生变化** | ❌ 误判为：清理法线损坏了原模型的阴影 | ✅ **正解**：外部导入工具残留的 Split Normals 往往包含损坏的法线数据导致黑斑。清除后方可正确应用 Blender 的 Auto Smooth 与材质法线。 | 若保留损坏法线，模型在添加修改器或进入编辑模式后将出现不可逆的面阴影断层。 |
| **插件在没有 Pillow 时弹出依赖提示而非直接崩溃** | ❌ 误判为：为什么不直接在最顶部 import PIL | ✅ **正解**：遵循插件沙盒安全原则，基础建模与 UV 功能纯原生运行，高级烘焙功能做延迟加载与优雅降级。 | 若顶层直接 import，缺失依赖的用户将完全无法启用插件的基础建模工具。 |
| **MC Baker 解析模型 UV 时 V 轴自动执行 $1.0 - v$** | ❌ 误判为：UV 翻转错误，导致材质上下颠倒 | ✅ **正解**：Minecraft JSON UV 原点为左上角，Blender UV 原点为左下角，V 轴必须翻转对齐。 | 若不翻转，所有方块顶面、侧面纹理在视口中将完全上下颠倒。 |
| **MC Baker 楼梯模型烘焙时自动切除内部重叠子面** | ❌ 误判为：为什么楼梯由多个 Element 组成却缺少内部接触面 | ✅ **正解**：多 Element 内部重叠区域为不可见隐藏体积，通过 2D 矩形求差集自动裁剪，消除 Z-fighting 撕裂。 | 若保留内部重叠面，导出 FBX 或启用透明材质时会出现杂乱的内部面片与双倍几何体。 |
| **Direct Mesh 握手成功时跳过全量快照重建** | ❌ 误判为：连接后为什么没有触发全场景重绘 | ✅ **正解**：Section CRC32 证明本地已有模型与服务端 100% 一致，短路跳过全量构建实现 0ms 极速连接。 | 若每次重连均强制推翻重建，大型场景会频繁卡顿甚至丢失用户在视口中调整的材质节点。 |
| **骨骼模型切分前必须调用 `bm.verts.layers.deform.verify()`** | ❌ 误判为：多余的代码调用 | ✅ **正解**：Blender BMesh 若未显式激活 deform layer，新细分生成的顶点将被剥离所有骨骼权重。 | 若移除该调用，细分切分后的皮肤角色骨骼蒙皮将出现局部顶点悬空脱节。 |
| **Live Sync 握手重连时自动增量修复局部差异方块** | ❌ 误判为：重连后为什么没有执行全场景重新下载 | ✅ **正解**：比对 Section CRC 发现局部差异区块时，自动发送 `0x81 PACKET_C2S_REQ_SECTION_SYNC` 仅请求有变动的区块并执行局部 BMesh 重构，实现毫秒级自愈。 | 若每次重连只要有局部修改就强制推翻全场景，稍大工程就会因数百个区块传输而出现长时间卡顿与视口重置。 |
| **Live Sync 微更新/高频红石期间严禁调用材质包哈希与磁盘校验** | ❌ 误判为：每次更新方块为什么不顺便检查一下材质包是不是被修改了 | ✅ **正解**：材质哈希校验属于冷阶段（连接/重构/打开工程）职责；热阶段必须保持纯内存纳秒级直通（`mat.as_pointer()` 指针缓存），严禁在 66Hz 主线程中计算 SHA256 或扫描 ZIP 文件。 | 若在微更新期间调用磁盘/哈希检查或清空烘焙缓存，高频红石时钟会引发致命的主线程 I/O 阻塞、掉帧与视口严重卡顿。 |
| **Live Sync 高频微更新仅刷新 `VIEW_3D` 视口，抑制 `PROPERTIES` 属性面板重绘** | ❌ 误判为：收到数据后应该对所有窗口和面板全量 `tag_redraw` | ✅ **正解**：Blender RNA 属性面板在高频重绘时会触发庞大的 Depsgraph 依赖图失效计算。高频红石期间仅需更新 3D 视口，保持 60+ FPS 流畅度。 | 若每次微更新均重绘属性面板，高频红石会引发依赖图重算风暴，导致视口掉帧。 |
| **Live Sync 运行中心跳校验（1s 间隔）绝不拉起进度条或打断 Delta 队列** | ❌ 误判为：收到服务器心跳 Manifest 时应该弹出进度条提示用户当前正在同步 | ✅ **正解**：心跳校验属于后台静默健康检查。若本地有未完成的在途 Delta 队列直接跳过比对；即便修复也完全在后台静默执行，绝不干扰用户视口。 | 若运行中心跳弹出 `ProgressBar.begin()`，每次在游戏里放下方块视口就会弹框闪烁并打断正在进行的红石同步。 |
| **选区平移/缩放时保留重叠区方块与 Mesh，仅裁剪超出边界的数据** | ❌ 误判为：选区变动了为什么不直接调用 `storage.clear()` 全部清空重拉 | ✅ **正解**：选区在微调、平移挪动或增减边界时，重叠区域的方块数据与场景 Mesh 具有绝对复用价值。仅需裁剪移出物体并对新接缝 Section 标记 dirty，大幅节省 CPU 与网络。 | 若每次微调选区均清空重构，用户在拖拽选区框时视口将频繁全量闪烁、反复推翻已建好的上百个区块。 |
| **流式构建中途选区改变时，双端必须原子中断旧流式任务并排空队列** | ❌ 误判为：等旧流式任务发完再发新的，或者多流并发 | ✅ **正解**：快速连续拖拽选区时，服务端通过 `activeBroadcastStreamId` 与 `cancel(true)` 原子中断旧流循环；客户端收到新选区瞬间排空积压队列并设置包围盒栅栏丢弃过期货，0 冗余 CPU 浪费。 | 若不执行原子熔断，多次构建在后台并发运行，服务端与客户端 CPU 飙升至 100%，视口严重卡死掉帧。 |
| **流式构建中途若队列暂时变空，严禁提前清空 `_dirty_sections`** | ❌ 误判为：队列空了说明当前批次完成了，可以提前 clear dirty | ✅ **正解**：流式网络传输存在微小包间隔，中途队列假空时必须保留 `_dirty_sections` 的累积；只有在服务端发送完毕（`is_batch_complete == True`）且全部区块到齐后，才统一触发终极接缝面自愈闭环。 | 若中途提前 clear，先到达的区块在邻居尚未入库时生成的暴露外表面将无法自愈，导致首次同步时区块接缝面剔除抽风失效。 |
